# Release workflow policy

The release workflow runs only from this shelf's exact current `refs/heads/main` so GitHub can issue a publicly verifiable artifact attestation. A dispatch from any other ref is skipped before credentials are available. The workflow accepts only an explicit signed `FutureDevGuys/homelab` source tag and receives no homelab decryption key. This shelf has no editable application source, package update, pull-request deployment, mutable mirror, or general automation workflow.

The build job has read-only shelf permission, mints a repository-scoped GitHub App token with read access only to `FutureDevGuys/homelab`, sparsely checks out `portable/` and the exporter, builds twice, validates the exact source identity and archive contents, renders clean extractions, and transfers only the five canonical release assets through GitHub's workflow-artifact service. It has no shelf write, attestation, or OIDC authority.

The publish job receives only the validated workflow artifact. It has no source checkout, source App token, or private-source execution path. Its ephemeral shelf `GITHUB_TOKEN` and OIDC identity revalidate and attest the exact asset set, create the shelf tag at the workflow's exact `main` commit through GitHub's create-only ref endpoint, require `gh release create --verify-tag`, create a draft, and publish only after independent download equality and another exact tag read. The completion gate rereads the published release, immutable state, exact tag target, asset names, sizes, provider digests, downloaded bytes, and the published manifest's exact private-source identity. Publication is a manual workflow action that the ordinary contributor App cannot dispatch.

An explicit signed `portable-vX.Y.Z` source tag produces deterministic tar and zip archives, a canonical source and archive-content manifest, an SPDX SBOM, `SHA256SUMS`, and GitHub-signed build provenance. The canonical allowlist has exactly those five assets; `SHA256SUMS` covers the four non-self-referential payload assets.

A release version is immutable. An administrator using a credential with repository `Administration(read)` must run the following official repository-scoped immutable release setting preflight before merge and immediately before every dispatch. If it does not return success, do not merge or dispatch. The publish workflow intentionally cannot perform this read because its ephemeral `GITHUB_TOKEN` must retain only release-publication authority; do not add Administration permission or another persistent publisher credential. See GitHub's [immutable-release repository API](https://docs.github.com/en/rest/repos/repos?apiVersion=2026-03-10#check-if-immutable-releases-are-enabled-for-a-repository).

```sh
test "$(gh api --header 'X-GitHub-Api-Version: 2026-03-10' repos/FutureDevGuys/compose-apps/immutable-releases --jq .enabled)" = true
```

The workflow refuses to report success unless the published provider object also confirms `.immutable == true`. That final read is defense in depth, not a replacement for the administrator preflight: the narrow workflow token cannot detect a settings change before tag reservation, and an administrator disabling immutability after preflight can cause the final gate to fail after publication. Treat that attempted release as unsafe, remove it through explicit administrator recovery, and publish only a corrected higher version. Do not dispatch while repository or organization release settings are changing.

GitHub documents drafts as the staging surface for immutable releases, but the draft release, its tag, and its assets remain mutable until publication. The workflow cannot close that provider window: the all-repositories contributor App and other repository writers can still hold Contents write even though they cannot dispatch this workflow. Immediately before dispatch, an administrator must establish a publication window with no concurrent contents-write actor modifying this repository's release, tag, or asset state, and keep it in effect until the final immutable-release verification completes. This is an operational prerequisite, not an authority claimed by the workflow. If the window cannot be established, do not dispatch.

The workflow rejects an existing release or tag, builds twice, validates clean archive extractions, reserves the shelf tag without overwriting any ref, creates a draft, downloads every asset for byte equality, rereads the tag, and then publishes. Prior published versions are outside the workflow's mutation target. A mismatch detected after tag reservation or publication burns the attempted version, requires explicit administrator recovery of any unsafe draft or release, and requires a corrected higher version. GitHub Releases is the canonical release catalog.
